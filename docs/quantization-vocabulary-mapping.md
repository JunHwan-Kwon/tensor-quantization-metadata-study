# Quantization vocabulary ownership at the CycloneDX 2.0 draft boundary

## Scope

This note measures the interaction between two pinned proposals:

- CycloneDX/specification PR #990 at commit `49a9456`, which introduces a
  typed quantization object; and
- CycloneDX/cyclonedx-property-taxonomy PR #175 at commit `378f7b4`, which
  defines string-valued quantization properties.

The six test documents describe one named external input parameter. They do
not evaluate internal tensor enumeration, inference behavior, task accuracy,
or the final text of either open pull request.

## Field crosswalk

| Meaning | PR #990 typed field | PR #175 property value |
| --- | --- | --- |
| method | `quantization.method` | no direct entry |
| nominal width | `quantization.bits` | no direct entry |
| affine class | `quantization.scheme = affine` | `scheme = affine_asymmetric` |
| symmetric class | `quantization.scheme = symmetric` | `scheme = affine_symmetric` |
| one contract per tensor | `granularity = per-tensor` | `granularity = per-tensor` |
| one contract per channel/axis | `granularity = per-channel` | `granularity = per-axis` |
| grouped quantization | `granularity = per-group`, `groupSize` | no direct entry |
| selected dimension | `axis` as an integer | `axis` as a decimal string |
| affine scale | no typed field | `scale` as a scalar string or JSON array string |
| affine zero point | no typed field | `zeroPoint` as a scalar string or JSON array string |

This table is a semantic crosswalk, not a claim that differently named values
are interchangeable in every framework. In particular, source-axis
normalization and per-group conventions remain separate design questions.

## Reproduced observations

All complete BOMs were validated against the 28-file modular schema graph at
PR #990 head, not against the stale bundled schema at that commit.

| Probe | Modular schema | Pinned taxonomy | Ownership observation |
| --- | --- | --- | --- |
| typed only | valid | not used | typed core only |
| typed plus `scale`/`zeroPoint` | valid | missing required taxonomy `scheme` | numeric extension without a taxonomy-valid property set |
| equivalent duplicated `scheme` | valid | valid | equivalent values stored in two sources |
| contradictory typed/property values | valid | valid | semantic contradiction is not rejected |
| per-tensor vector scale | valid | invalid value form | property value shape is outside the typed schema |
| earlier aggregate `modelCard` placement | invalid | legacy aggregate placement | no named parameter binding in the current draft |

The result establishes three narrow facts:

1. Typed quantization and sibling parameter properties can coexist in the
   current modular schema.
2. The schema permits both equivalent duplication and contradictory
   duplication.
3. PR #175 currently requires its string-valued `scheme` whenever another
   quantization sub-property is used, so `scale` and `zeroPoint` alone are not
   taxonomy-conforming even when typed `scheme` is present.

The result does not establish maintainer intent. That remains a design
decision rather than a validation outcome.

## Design options

### A. Typed ownership with numeric property extension

The typed object owns `method`, `bits`, `scheme`, `granularity`, `groupSize`,
and `axis`; parameter properties carry only affine values not represented in
the typed object. This avoids duplicated classifications but requires PR #175
to recognize the typed `scheme` or relax its local `scheme` requirement.

### B. Taxonomy ownership for the complete affine contract

The typed object is limited to non-overlapping fields, while taxonomy
properties own scheme, granularity, axis, scale, and zero point. This keeps
the affine mapping together but gives up typed validation for those fields
and leaves grouped vocabulary alignment to be resolved.

### C. Deliberate duplication with an external consistency rule

Both representations remain legal and producers repeat overlapping values.
This is backward-compatible with the measured schema behavior, but the
relationship between typed JSON values and arbitrary string-valued property
arrays is not generally enforceable as semantic equality by the current JSON
Schema. A separate semantic validator and explicit precedence rule would be
required.

Mutual exclusion is structurally enforceable with JSON Schema conditionals.
Cross-representation semantic equality is a different problem and must not be
described as if ordinary schema validation already provides it.
